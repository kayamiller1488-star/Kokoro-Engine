# Voice latency baseline — 2026-11-22

The reference numbers for "how fast does she answer", broken down by stage so a future change
of mouth, brain or ear can be compared against something real instead of a feeling.

Measured on the machine that runs the character, with the game **not** competing for the GPU
unless noted. Every number below is wall-clock from a live service, not an estimate.

## Stack at the time of measurement

| piece | what it was |
|---|---|
| Brain | llama.cpp, `Qwen3.5-4B-Q4_K_M`, ctx 65536, port 8091 |
| Ear | SenseVoice-small int8 (CPU, 16 kHz) for English; faster-whisper `large-v3-turbo` (CUDA fp16) for Japanese, port 9882 |
| Mouth | Kokoro-ONNX (`af_heart`+`jf_alpha` for kana), CUDA execution provider, port 9881 |
| Shell | Kokoro-Engine (Tauri), mod `va-voice-aec`, debug port 9222 |

Commits: src-repo `0cf75b9`, va-ears `c88c3f4`, va-mouth `68ce6b3`.

## Idle vs GPU-busy (same build, re-measured after the owner stopped gaming)

The first table was taken with a game holding the GPU. The same services, measured idle, are
visibly faster — which matters because a future comparison against load figures would look like a
regression that never happened:

| stage | busy median | **idle median** | change |
|---|---|---|---|
| Ear — Japanese (whisper) | 195 ms | **161 ms** | −17 % |
| Ear — English (SenseVoice) | 146 ms | **145 ms** | −1 % (CPU, unaffected) |
| Brain — full reply | 295 ms | **191 ms** | −35 % |
| Mouth — 20 chars Japanese | 147 ms | **126 ms** | −14 % |
| Mouth — 24 chars English | 295 ms | **158 ms** | −46 % |
| App orchestration + brain | 979 ms | **828 ms** | −15 % |
| App turn (text in → first audio) | 1906 ms | **1033 ms** | −46 % |

Idle end to end for a spoken Japanese turn:

```
VAD 650 ms  +  ear 161 ms  +  orchestration+brain 828 ms  +  mouth 126 ms  ≈  1.77 s
```

Directly measured app-side (text in → first audio) is 1033 ms, which is orchestration + brain +
mouth, so the two agree to within a few tens of milliseconds.

**Use the idle column as the reference.** Quote the machine state with any number you take.

## End to end

Directly measured inside the app (text submitted → her first audio sample, 5 turns):
**1906 ms median** (997–2428).

Composed from the stages for a spoken Japanese turn:

```
VAD 650 ms  +  ear 189 ms  +  orchestration+brain 979 ms  +  mouth 150 ms  ≈  1.97 s
```

Both agree: **about 2 seconds from the moment you stop talking to the moment she starts.**
Of that, the models are only ~0.6 s; the remaining ~1.4 s is fixed waiting (0.65 s VAD) and the
app's own orchestration (~0.7 s).

## What this means for swapping parts later

- A faster **mouth** can win at most ~0.15 s — it is not the bottleneck.
- A faster **brain** can win at most ~0.28 s on the full reply (~0.10 s to first token), unless the
  shell is switched to speak per sentence while generating, which would hide most of it.
- A better **ear** costs +0.05 to +0.17 s versus SenseVoice and buys accuracy on accented
  Japanese; that is the only stage where paying more time has clearly paid off so far.
- The two biggest single wins left are not models at all: shortening `SILENCE_S` (0.65 s) and
  finding the ~0.7 s inside the app between receiving a transcript and calling the brain.

## Cloud brain measured against the same stack (2026-11-22, same evening)

Route: shell → `va-brain/relay.py :8092` → `https://opencode.ai/zen/go/v1`, model `glm-5.3-flash`.
Everything else (ear, mouth, VAD, persona) unchanged; the local 4B was stopped afterwards.

| | local 4B | glm-5.3-flash, thinking **on** | glm-5.3-flash, thinking **off** |
|---|---|---|---|
| first spoken token (streamed, real persona) | 101 ms | ~1210–1482 ms | **1219 ms** |
| full reply | 191 ms | 1909–2410 ms | **1925 ms** |
| output tokens | ~22 | 248 (214 of them reasoning) | 26 |
| app turn (text in → first audio) | 1033 ms | 1619 ms (median of 3) | 2109 ms (median of 4, spread 720–2547) |
| prompt tokens per turn | n/a | 1532 | 1532 |
| cost per turn | 0 | — | **$0.00024** |
| VRAM released | — | — | **~8.1 GB** (brain stopped; measured free 770 → 3987 MiB with a game running) |

Notes that matter for reading these numbers:

- **Prompt size sets the floor.** With a 19-token prompt the cloud answers in 656 ms to first token; with
  her real 1532-token persona it is 1219 ms. The persona is ~85 % of the tokens, so any latency work on
  the cloud route is prompt-trimming work.
- **Thinking on is not free but it is not fatal either**: 214 reasoning tokens, ~+0.6 s. It also risks
  `content: null` if the budget is small, which is why the relay floors `max_tokens` at 900 and retries
  once, wider, when a reply comes back empty.
- **App turns are noisy** (720–2547 ms). The shell speaks per sentence as the stream arrives, so a short
  first sentence is audible in <1 s even though the full reply takes ~2 s.
- Cost is billed per token and reported by the endpoint (`usage.opencode.list_cost`). A conversation at a
  turn every 10 s costs roughly $0.09/hour.

### Switching routes

```bash
# cloud, thinking off (default)
cd /c/Projects/va-brain && MODE=cloud THINKING=off python relay.py
# cloud, thinking on
MODE=cloud THINKING=on python relay.py
# back to the local 4B
MODE=local python relay.py
```

The shell always points at `http://127.0.0.1:8092/v1` with model `cloud`; per-request routing also
works (a model name containing `local` goes to llama.cpp, `cloud` to the endpoint).

Reopening the local brain after it was stopped: `powershell -File C:/Projects/va-brain/serve-brain.ps1`.
